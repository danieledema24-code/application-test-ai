# API contracts

Base URL: `http://localhost:8200/api/v1`. JSON only (UTF-8). OpenAPI generated by FastAPI at `/api/v1/openapi.json` and is the machine-readable contract; this document is the design intent.

## Conventions

- **Auth**: `Authorization: Bearer <session token>`. Token = 32 random bytes, base64url; server stores only its SHA-256 (`sessions.token_hash`). Lifetime 12 h, sliding refresh on use after 1 h, revocable. Every endpoint requires auth except `health`, `auth/register`, `auth/login`, `auth/forgot-password`, `auth/reset-password`, and signed evidence/report content URLs.
- **Tenant**: the session's active organisation. Resources in other organisations return `404`.
- **Roles**: `viewer` read-only; `member` create/run/edit; gate approvals need `can_approve` (owners/admins have it by default).
- **Errors** (all non-2xx):
  ```json
  { "error": { "code": "validation_error", "message": "Human-readable summary", "details": [{"field": "url", "message": "..."}], "request_id": "01J..." } }
  ```
  Codes: `validation_error` 422, `bad_request` 400, `unauthenticated` 401, `forbidden` 403, `not_found` 404, `conflict` 409 (version mismatch, stage already running), `gate_blocked` 409, `DUPLICATE_PROJECT` 409 (see `POST /projects`; the one upper-case code, agreed with the web client), `url_blocked` 422 (SSRF policy), `url_unreachable` 422, `rate_limited` 429 (+`Retry-After`), `internal` 500 (no internals leaked).
  `details` is a list of `{field, message}` objects, except for `DUPLICATE_PROJECT`, where it is an object (below). Every response carries an `X-Request-ID` header equal to `error.request_id`.
- **Pagination**: `?limit=20&cursor=<opaque>` → `{ "items": [...], "next_cursor": "..." | null }`. Max limit 100.
- **Concurrency**: mutable resources return `version`; `PATCH` bodies include `version`; mismatch → 409.
- **Timestamps**: ISO 8601 UTC. **IDs**: UUID strings; human keys (`SCAN-0001`) in `key`.
- **Provenance fields** on every AI-derived item: `provenance`, `confidence`, `evidence_refs`, `generated_by` (`ai` | `rules` | `human`). The UI must label `rules` output ("Generated by rules, AI not configured").

Shared schemas (Pydantic style):

Always `200` with a result (blocked/unreachable are data, not errors). Uses `httpx` with `follow_redirects=False`, manual hop validation (max 5), 10 s timeout, 1 MB body cap, `GET` only. The DNS lookup of each hop is bounded by the same timeout (`unreachable_code: "dns_timeout"`).

`POST /projects` — the "Start QA Analysis" action
```python
class ProjectCreate(BaseModel):
    url: str
    name: str | None = Field(None, max_length=120)      # default: host name / page title
    description: str = ""
    authorisation: AuthorisationAttestation
    scan: ScanSettings = ScanSettings()
    start: bool = True                                    # immediately enqueue intake -> discovery
    confirmDuplicate: bool = False                        # camelCase on purpose (web client); `confirm_duplicate` also accepted
    credentials: {"login_url": str, "username": str, "password": str} | None = None
        # all three or none (else 422 per field); login_url must be on the site's host. Stored AES-GCM encrypted,
        # never returned. Phase 1 discovery does not sign in; the credentials are kept for later phases.

class AuthorisationAttestation(BaseModel):
    attested: Literal[True]                               # must be true
    statement: str = Field(min_length=10, max_length=500) # e.g. "I own example.com" (UI pre-fills)

class ScanSettings(BaseModel):
    max_pages: int = Field(30, ge=1, le=100)              # also capped by organisation.limits (default 30 per design)
    max_depth: int = Field(3, ge=0, le=5)
    include_mobile: bool = True
    respect_robots: bool = True
```
→ `201 ProjectDetail`. Server re-runs the URL check; if not `allowed` → 422 `url_blocked`; if unreachable → 422 `url_unreachable` (the project is not created). Records G1 decision (`approve`, by the user, with automated check result), audit `project.created` + `gate.approved`. If the organisation is at its concurrent-scan limit the project is still created and the discovery stage stays `queued` (the worker enforces the limit; an `agent_event` explains the wait). Errors: 429 on the project-creation rate limit; 409 `DUPLICATE_PROJECT` if a non-archived project in the organisation has the same normalised (or final) URL and `confirmDuplicate` is not `true`. Its `details` is an object: `{"project_id": UUID, "project_name": str, "primary_url": str, "field": "url"}`. Resending with `confirmDuplicate: true` creates a second project.

### Live progress channel (SSE)

`GET /projects/{id}/events/stream` — `Content-Type: text/event-stream`. Auth via `Authorization` header (client uses `fetch` streaming, not `EventSource`). Resume with `Last-Event-ID` header or `?after=<id>`. Server tails `agent_events` (poll 500 ms, or wake-up signal) and sends a `: keep-alive` comment every 15 s. Connection closes after 30 min; client reconnects with the last id.

```
id: 1842
event: agent_event
data: {"id":1842,"project_id":"…","stage_key":"discovery","agent_key":"discovery","task_id":"…",
       "type":"page.discovered","level":"info","message":"Found page \"Pricing\" (/pricing)",
       "data":{"page_id":"…","url":"https://example.com/pricing","screenshot":{"id":"…","content_url":"…"}},
       "created_at":"2026-11-12T10:15:03Z"}
```

Event types (Phase 1): `stage.status_changed {stage_key, from, to, version}`, `task.started`, `task.progress {done, total, label}`, `task.completed`, `task.failed {reason}`, `page.discovered`, `page.failed {url, reason}`, `evidence.captured`, `request.blocked {url, reason}`, `gate.awaiting_approval {gate, recommendation}`, `gate.decided`, `report.ready`, `log` (agent narration, user-readable). Event `data` never contains secrets or raw page text.

Non-streaming fallback: `GET /projects/{id}/events?after=<id>&limit=100` → `{items: [AgentEvent], next_after: int}` (also `?before=<id>` for paging backwards). Org-wide activity: `GET /activity?limit=&cursor=&milestones=true|false`.

Phase 1 notes on event `data`: every event has `kind` (`status`, `action`, `finding`, `warning`, `error`, `gate`); findings carry `label` (`observed`/`inferred`), `path` and `evidence_ids`. `page.discovered` carries `screenshot: {"id", "content_url"}`; the URL is re-signed whenever events are read (list or stream), so replayed events never hold an expired link. `task.progress` carries `done, total, label, screenshots, queued`.

### Phase 1 additions (implemented, additive)

These fields were added by the Phase 1 backend. All are optional for clients and none change an existing field's meaning. The OpenAPI document at `/api/v1/openapi.json` is authoritative.

- `Health.worker.mode` may also be `"off"` (no worker in this process). `Health.allow_private_targets` (see Health).
- CORS: `WEB_ORIGIN` may send `Authorization`, `Content-Type`, `Accept`, `Cache-Control`, `Last-Event-ID`, `X-Request-ID` (the SSE fetch sends `Cache-Control` and `Last-Event-ID`); `X-Request-ID` and `Retry-After` are exposed.
- `ScanDetail.partial: bool | None`: true for cancelled, time-limited, failed or page-limited scans (unvisited frontier); false when the whole site was seen; null while running. Same rule as the report's `content.partial` / `ReportSummary.partial`.
- `ScanDetail.stop_reason`: `page_limit | exhausted | cancelled | timeout | paused | failed` (null while running). The G2 recommendation's advice follows it (re-run after cancel/time limit/error, higher page limit only after the page limit, credentials when areas need sign-in). Limitations, completeness, access gaps and the sitemap's not-visited reason follow it; "page limit" is only reported when the limit was actually reached.
- Auth boundaries vs access gaps: a sign-in page that loaded is reported in `auth_boundaries` (`kind: login_form`) and its page has `requires_auth: false`; it is not an access gap. Access gaps with reason `Needs credentials` are the URLs that answered 401/403 or redirected to sign-in; when the only sign-in signal is a visible form, there is exactly one such gap, `area: "Signed-in area behind /login"`, suggesting test credentials. The same areas drive the G2 line "N area(s) need credentials", the summary and the "Some pages need a sign-in…" limitation.
- `ProjectSummary`: `access_gaps: int`, `scans: int`, `current_activity: str | None` (latest narration while running).
- `ScanSummary`: `number`, `stage_run_version`, `created_at`, `is_latest`. `ScanDetail` adds `summary`, `summary_generated_by`, `skipped_links: list[{url, reason}]` (reasons: `would end the session`, `destructive action`, `file download`, `robots.txt`, …), `external_links`, `not_visited: list[str]` (URLs left in the frontier), `injection_flags`, `robots`, `queue_position`, `gate`, `project_id`. `stats` adds `pages_failed, dropdowns, tabs, pagination, components, screenshots, queued, access_gaps, elapsed_s`. `completeness` adds `checks: list[{status: ok|warn|fail, text}]`. `current` adds `screenshot`.
- `AccessGap` adds `area`, `reason` (fixed vocabulary: `Needs credentials`, `Not performed: destructive or transactional action`, `Not visited: page limit`, `Not visited: discovery cancelled`, `Not visited: time limit`, `Not visited: discovery stopped early`, `Not visited: robots.txt`, `Blocked by bot protection`, `Outside scope (blocked address)`, `Couldn't load (…)`), `evidence_refs`. `AuthBoundary` adds `login_url`.
- `PageSummary` adds `path`, `status: visited|failed|blocked`, `failure_reason`; `PageDetail` adds `links`, `scan_id`. Form field `constraints` adds `minlength`.
- Journey steps add `label: observed|inferred` (a step that was navigated is observed; filling or submitting a form is inferred, never performed).
- `DiscoveryReportContent` adds `site, organisation, project, scan, gate1, approval, counts, key_observations, partial, partial_notice, mobile_included, generated_at, glossary, recommendation`.

## Phase 2 endpoints (full detail)

All Phase 1 conventions apply: bearer auth, the session's organisation as tenant (other organisations get 404), the error envelope, `?limit&cursor` pagination returning `{items, next_cursor}`, `version` on mutable resources (a mismatch is 409 `conflict`), snake_case, ISO 8601 UTC, and signed content URLs for files. Role rules: `viewer` read only; `member` runs, edits, approves or rejects individual items, uploads and accepts proposals; gate decisions and test-credential management need `can_approve` (owners/admins by default). Writes by a viewer return 403 `forbidden`. Every write is audited (action names below).

### Workflow additions (P3-00)

- `POST /projects/{id}/stages/test_design/run` with the Phase 2 `StageRunRequest` body: `{reason?, parameters?: {guidance?: str (≤ 1000)}}`. Test design also starts automatically when G4 is approved and the stage has never run.
  - 409 `gate_blocked` "Test strategy approval (G4) must be approved first".
  - 409 `conflict` if a test design candidate is pending review.
  - `traceability` cannot be run: 422 "Traceability is computed automatically".
- The change review endpoints (`/stages/test_design/runs/{version}/review`, `/apply`, `/discard`) work as in Phase 2. Items are typed `test_condition`/`test_case`/`test_data`.
- `GET /projects/{id}/stages/test_design/runs/{version}` `output` = `{counts: {conditions, cases, data, by_technique, by_type, by_status}, not_designed: list[{test_type, reason}], lint: {errors, warnings}, diff: RegenerationDiff}`.
- **G5 is a required sign-off (decision D1).**
  - `DEFAULT_APPROVAL_POLICY.G5 = "required"`. New projects store it, and existing projects are switched by a startup data step (see roadmap P3-00).
  - When design output is produced, `test_design` goes to `awaiting_approval` with gate `pending`.
  - Phase 4 stages treat `test_design` as gate-satisfied only when it is `approved`.
  - `PATCH /projects/{id}` may still set G5 to `recommended`/`auto` (G5 is not a locked gate).
- `POST /projects/{id}/gates/G5/decision`: same body as G3/G4. **Permission:** `can_approve`, the same check as G3/G4. Without it you get the existing 403 "You don't have permission to approve quality gates. Ask an owner or admin."
  - **Blockers**:
    1. G4 approved, and the design's `approved_input` matches it
    2. ≥1 approved case
    3. no approved case with a blocking lint item
    4. every approved requirement linked to an open high/very-high risk has ≥1 approved case
    5. no open-question case among draft **or** approved cases (`code: "open_questions"`; decision D6, settled by the P3 design)
  - **Warnings**: drafts remain; approved requirements without an approved case; approved ACs without a case; lint warnings on approved cases; accepted high risks without an approved case.
  - Precondition codes: `g4_approved`, `approved_case`, `approved_lint_errors`, `open_questions`, `high_risk_covered` (blocking); `drafts_remaining`, `requirements_without_case`, `acs_without_case`, `drafts_with_errors`, `approved_lint_warnings`, `accepted_risks` (warnings).
  - `StageState.approved_input` for `test_design` = `{stage_key: "test_strategy", snapshot_hash, version, requirements_snapshot_hash, requirements_version}`.
  - The `gate.awaiting_approval` event reads "… is waiting for approval" (no role is implied; the UI words it from `can_approve`).
  - On approval, the TCS and RTM frozen reports are queued.
- `StageState.gate.preconditions` and `changes_since_approval` are computed for G5 as for G3/G4.

### Phase 6 backend notes (as built, P6-00)

- `CURRENT_PHASE = 6`. `GET /projects/{id}/workflow` lists three `phase: 6` stages, all `available`: `release_readiness` (G9, locked to `required`), `change_analysis` and `exploratory` (both upstream `discovery`, no gate). Their status stays `not_started` until P6-01 / P6-03a / P6-05a.

It is exempt from the G2 gate like the discovery report (the change set is part of what a person reviews at G2). A plain discovery re-run never queues it. Until P6-01 registers its handler, `advance()` skips it and `POST /stages/change_analysis/run` answers 409 `gate_blocked` before G2 and 422 "Change analysis is not available yet" after.
- `exploratory` is an optional, run-driven branch like `accessibility`: `advance()` never queues it, and `POST /stages/exploratory/run` answers 422 "Start an exploratory session from Test Execution".

Unknown fields: 422.
- `release_readiness` is never queued by `advance()`. `POST /projects/{id}/release-assessments` (member, no body) and `POST /stages/release_readiness/run` answer 409 `conflict` "Run the tests first: release readiness needs execution results" until at least one execution run has finished (`passed` or `failed`; runs waiting for G7, refused, errored or cancelled don't count), then 422 "Release readiness assessment is not available yet" until P6-05a.

A plain discovery re-run (`POST /stages/discovery/run`, whose `parameters` can't carry `rescan`: `ScanSettings` forbids unknown keys) keeps the Phase 5 behaviour: every finished downstream stage goes `stale` ("Application discovery was re-run (version n)").

- Scan ref: `{id, key, number, status, partial, is_rescan, pages, started_at, finished_at, created_at, g2_approved, baseline}`. `ScanSummary` (`GET /projects/{id}/scans`) gains `is_rescan`, `baseline_number` and `g2_approved`.
- `ChangeSet`: `{id, key, status (queued|running|completed|failed), source (rescan|compare), base, target, summary {total, by_significance, by_kind, content_values, pages {baseline, target, added, removed, changed, not_compared, structural, baseline_compared}}, not_compared [{page, url, missing_from, reason}], rebaseline_suggested, generated_by: "rules", ai_summary {text, generated_by: "ai"}|null, started_by, created_at, finished_at, error, statement (CHANGE_STATEMENT), permissions {can_compare}}`.
- `ChangeItem`: `{id, kind, display_kind (added|removed|renamed|moved|changed|requirement_changed|content_values), significance, page_url, page, subject, before, after, before_ref, after_ref}`; refs carry `{page_id, url, fingerprint, screenshot, dom}` evidence links. `subject` is the written-out change ("Field changed: Message → Your message (now required)").
- Matching (D26): pages by URL hash and sign-in context; components deduplicated, then paired one-to-one by fingerprint, then kind + role + selector (a rename), then kind + role + name (a move). Links outside navigation are compared by path and named after their target page. Forms by action + method, then label; fields by name. Navigation is the union of nav links over all pages. Journeys by name + start path; digits in paths are normalised.
- Significance: structural = page, form, field or element added or removed, field type/required/constraint/option change, status code change; behavioural = renames, label-only field changes, submit label, navigation, journeys; cosmetic = headings, moves (behavioural when an automation script's `locator()` uses the selector) and content values. The noise filter folds names that differ only in numbers or currency into one cosmetic `page_changed` item per page with `after.group = "content_values"`.
- Partial scans (OQ2): pages only one scan has, when the other stopped early (or was cancelled or failed), are listed in `not_compared`, never as added or removed, and have no items; so are pages the other scan listed as `blocked`. A journey through a page that wasn't reached is not compared either.
- A cancelled or failed rescan makes no change set (design P6 §5): `change_analysis` is not queued for it (and does nothing if run).
- An interrupted `change_analysis` task or `change_compare` job leaves its set `failed` ("interrupted"); comparing the pair again then creates a new set (only sets that are not `failed` are reused).
- Workflow: the discovery stage's `gate` (G2) carries `ever_approved` (any scan approved at G2). The web offers only "Rescan and compare…" when it is true (OQ1), independently of the scan list.
- `advance()` is serialised per project inside a process and retried once on a unique-version conflict with another writer (a gate decision racing the worker returned 500 on `stage_runs (workflow_stage_id, version)`).
- Re-baseline is suggested when removed pages plus matched pages with a structural item are more than half of the baseline pages compared. Added pages don't count.
- `change_analysis` (D27): queued once when a rescan finishes and compares that scan with its baseline. `POST /stages/change_analysis/run` answers 422 "Rescan the site, or compare two scans from Application Discovery › Changes". A plain discovery re-run never marks `change_analysis` stale (a change set compares two fixed scans) and never re-queues it.
- AI summary: optional, counts as placeholders filled by the platform; a summary with a digit or an unknown placeholder is dropped. Events `change.status`, `change.ready` ("CHG-0001 ready: 9 changes between Scan 1 and Scan 2 (…)"); audit `change_set.created`. Applying a requirements regeneration appends `requirement_changed` items to the latest completed set whose target scan is not newer than the regeneration.
- Rule-path naming on the demo shop: the journey is "Contact the company" (design §14 says "Contact us").
